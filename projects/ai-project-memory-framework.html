The AI Project Memory Architecture Framework

A robust, drift-free persistent memory system for autonomous AI coding assistants

Authored by: Nitish Kashyap R · Lead Architect & AI Systems Specialist · nitishkashyapr.com · Applicable: Antigravity, Claude Code, Cursor, Windsurf, OpenCode
Executive Summary: When building complex production software with AI coding assistants, models frequently encounter session amnesia, context drift, and hallucinated decisions. This architecture establishes a battle-tested 3-Pillar Autonomous Memory System to guarantee absolute alignment across hundreds of development sessions:
  • Pillar 1 — The Living Knowledge Base (PROJECT_MEMORY.md): Single source of truth preserved at the repository root.
  • Pillar 2 — The Sandboxed Subagent (memory-keeper): Dedicated agent with restricted permissions for audits and atomic updates.
  • Pillar 3 — Session Lifecycle Hooks (AGENTS.md): Deterministic triggers for session start, active work, cascade sync, and session end.

1 Pillar 1: The Durable Artifact (PROJECT_MEMORY.md)

Instead of relying on ephemeral chat context, hidden vector embeddings, or lossy summarizations, project truth is preserved in a clean, human-auditable markdown file at the repository root. This file serves as the canonical memory bank for every AI session.

PROJECT_MEMORY.md — 4-Section Canonical Schema Markdown 
# Project Memory & Architecture Standards (`PROJECT_MEMORY.md`)

## 1. Overview
High-level purpose, active project goals, stakeholders, and baseline constraints.

## 2. Core Architecture & Tech Stack Rules
Design systems, CSS tokens, performance budgets (Core Web Vitals), WCAG 2.1 AA accessibility, and SEO directives.

## 3. Installed Skills & Tooling Suite
List of active agent skills, plugins, and custom tool suites configured and enforced in the workspace.

## 4. Custom Rules & Regulations (Append-Only Numbered Directives)
1. **[Rule Name]**: Specific non-negotiable constraint or architectural requirement.
2. **[Rule Name]**: Durable decision recorded from past sessions; never renumbered or pruned without approval.
Human Auditable
Reviewable in plain text by engineering leads at any time; zero black-box vector stores or opaque embeddings.
Git Versioned
Every single update generates an explicit, line-by-line reviewable diff in standard version control history.
LLM Optimized
Zero token bloat; clear imperative phrasing (MUST, NEVER) ensures deterministic agent constraint adherence.

2 Pillar 2: The Dedicated Sandboxed Subagent (memory-keeper)

Core Design Principle: The main orchestrator agent never modifies project memory directly. It delegates all memory verification, synchronization, and updates exclusively to the dedicated memory-keeper subagent.
.agents/agent/memory-keeper.md — Permission Mask & Mandate YAML Frontmatter + Prompt 
---
description: Maintains the project memory file. Reads, verifies, and updates PROJECT_MEMORY.md checking it against actual project state.
mode: subagent
permission:
  edit:
    "*": "deny"                    # Strict lockdown: Zero write access to source code or assets
    "PROJECT_MEMORY.md": "allow"       # Exclusive single-file edit permission
  bash: deny                        # Cannot execute shell commands or git operations
  webfetch: deny · websearch: deny · todowrite: deny
---
You are the Memory Keeper for this project. You are the sole owner of `PROJECT_MEMORY.md`.

## Operational Responsibilities:
1. Read: Ingest `PROJECT_MEMORY.md` in full at the start of every dispatch.
2. Verify: Cross-reference facts against actual repository source code (Single Source of Truth).
3. Fix & Update: Correct drift in entity counts, dates, names, or file inventories; record durable rules.
4. Preserve Structure: Keep headers intact; append new rules sequentially (1., 2., ...); never renumber or delete.
5. Report: Return a concise summary of what was synced or "No changes needed".
Strict Scope Isolation Only edit PROJECT_MEMORY.md. Never request or accept write access to source code or assets.
Durable Fact Filtering Do not log conversational chatter—only record durable, future-useful architectural facts.
Zero Git Authority Never execute git commands (commit / push). Requires explicit human instruction.

3 Pillar 3: Session Lifecycle & Synchronization Protocol (AGENTS.md)

Phase 1 Session Start: Grounding & Drift Audit
Orchestrator dispatches memory-keeper before initiating user tasks to verify PROJECT_MEMORY.md against live code and resolve stale data.
Phase 2 During Session: Isolated Execution
Main agent writes production features, runs tests, and refactors UI without modifying memory files, ensuring speed and zero doc contamination.
Phase 3 Cascading Synchronization
When core domain data or schemas change, updates propagate across file owners deterministically:
Source of Truth (Code) → Domain Sync Agents → Memory Keeper
Phase 4 Session End: Fact Recording
Before session close, memory-keeper extracts durable decisions, updates entity counts, and appends new numbered rules to Section 4.

5 Key Architecture Invariants & Best Practices

These five architectural invariants are strictly enforced by the system to maintain absolute data integrity across long-running project lifecycles:

Best Practice Implementation Mechanism Architectural Value & Rationale
Append-Only Rules Data Integrity Sequential numbered list (1., 2., ...) in Section 4; never renumber, overwrite, or prune without explicit approval. Prevents silent regression of historical design constraints, tech stack boundaries, and user preferences across long conversation threads.
Single Source of Truth Grounding Memory is actively audited and verified against real repository source files on every session boot. Eliminates hallucinated assumptions, stale counts, and out-of-date documentation by grounding memory strictly in live executable code.
Strict Sandboxing Security Subagent permission mask grants write access exclusively to PROJECT_MEMORY.md (deny *). Guarantees zero accidental side-effects, syntax breakages, or unintended file overwrites in production application code.
Zero-Touch Git Governance Subagents are strictly denied bash and git execution permissions (commit, push). Keeps the human developer in complete sovereign control over version control history, commit messages, and deployment triggers.
Cross-IDE Portability Interoperability Standard Markdown format with declarative YAML frontmatter and standard prompt structures. Functions seamlessly and interchangeably across Google Antigravity, Claude Code, Cursor, Windsurf, OpenCode, and GitHub Copilot.

Why This Pattern Outperforms Vector Databases: Traditional RAG and vector database memory injects unbounded, noisy semantic chunks into prompt windows, frequently causing hallucination, token exhaustion, and context pollution. By enforcing a git-tracked, human-auditable markdown artifact maintained by an isolated, sandboxed subagent, teams achieve deterministic zero-drift persistent alignment at zero infrastructure cost.
